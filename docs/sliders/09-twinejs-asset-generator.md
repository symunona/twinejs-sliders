# 09 — Asset generator (twinejs fork)

Lives in the fork, next to the asset manager ([03](03-twinejs-asset-manager.md)) and the
image editor it reuses.

## Why it exists

A visual novel needs a lot of art, and most of it is placeholder for a long time. The
generator makes the placeholder in the editor rather than in another tab, so the image
that comes out is one click from being a `bg:`, an object, or a character.

## No server

Requests go from the browser straight to Google or OpenAI. There is no Twine backend and
there never will be one — a key posted to somebody else's host is a key you have given
away. Both APIs allow cross-origin calls with the key in a header, so nothing sits in
between.

Keys live in preferences (`geminiApiKey`, `openAiApiKey`), which means local storage, in
the clear, like every other preference. The Preferences dialog says so. This is a local
authoring tool; the threat model is "somebody else uses this browser profile", not "an
attacker reads the disk".

## Models

`models.ts` is a list, not a switch. Each entry names its provider, its request shape
(`gemini-generate`, `imagen-predict`, `openai-image`), and whether it takes reference
images.

**A model id not on the list is allowed.** Type one into the search box and the generator
guesses its request shape from the provider and the id prefix. Image models ship faster
than a hard-coded list gets updated, and a wrong guess fails with the provider's own error
message rather than with silence.

Models whose provider has no key stay in the list, greyed out. Seeing that Imagen exists
is how an author finds out they want a Google key.

## Aspect ratio

One control, three translations:

| API | How it is sent |
|---|---|
| Gemini image models | `generationConfig.imageConfig.aspectRatio` |
| Imagen | `parameters.aspectRatio` |
| OpenAI | nearest of `1024x1024` / landscape / portrait |

A model that has no aspect parameter (the 2.0 preview) is told in the prompt instead.

## History is not the library

Generated images go into their own IndexedDB database, `sliders-generations`. They are
**not** assets: they don't appear in the asset manager, they aren't bundled with a story
([08](08-export-import-bundle.md)), and they aren't in any manifest.

Most of what a model returns is a near miss, and a library full of near misses is worse
than no library. History is a scratchpad with a delete button. Three save buttons per
tile move an image across the line deliberately:

| Button | What it does |
|---|---|
| Save as Background | `putAsset({kind: 'bg'})` |
| Save as Object | `putAsset({kind: 'object'})` |
| Save as Character | frame asset + `putCharacter`, sized from the image |

Saving the same image twice hits the asset store's content-hash dedupe and re-points at
the existing asset rather than making a copy. The tile says so instead of pretending.

## Editing before saving

Background removal, crop and levels already exist in the image editor
([03](03-twinejs-asset-manager.md)), so **Edit** opens that editor on the generated bytes
rather than growing a second copy of it. In that mode the editor has no asset to write
back to, so its two library saves are replaced by one **Apply Edit**, which returns the
edited bytes to the history entry. Nothing reaches the library until a save button is
pressed.

## Attachments

Assets can be attached to a prompt as reference images — "the same character, now sitting
down" is the main reason anyone generates a second image. Character frames are included in
the picker for exactly that reason.

Attachments are only sent to models that accept them. Attaching to Imagen would otherwise
look like it had been taken into account.
